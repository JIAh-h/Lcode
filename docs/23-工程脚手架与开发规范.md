## 1. 这份文档要解决什么

[20](./20-模块设计与接口清单.md) 讲了模块边界，但没有讲"**代码放哪、怎么跑、怎么提交、CI 卡什么**"。

这份文档的目标是可验证的：**一个新研发拿到仓库，30 分钟内能跑起开发环境，2 小时内能提交第一个通过全部门禁的 PR。**

## 2. 仓库结构

与 [00 §5](./00-文档总览与全局约定.md) 的包布局一致，加上工程配套目录：

```
lcode/
├── packages/                 # 全部 @lcode/* 包（按 group 分目录）
│   ├── core/                 # 骨架层（7 个包，产品契约）
│   ├── llm/  fs/  shell/  sandbox/  terminal/  subprocess/
│   ├── context/  compaction/  spill/  skill/  subagent/  jobs/  web/  lsp/
│   ├── session-persistence/  interaction/  settings/  credentials/
│   ├── preset/  extension/  bundle/  util/
├── apps/
│   ├── desktop/              # Electron：main / preload / renderer
│   └── cli/                  # headless CLI
├── examples/                 # 可运行的最小组合（装配 yml 叶子）
├── docs/                     # 本套设计文档
│   └── tools/check.py        # 文档集校验脚本（链接 / 原型 / 术语）
├── prototype/                # 高保真原型（HTML，非产品代码）
├── scripts/                  # 仓库级脚本（门禁、生成器、发布）
├── fixtures/                 # 测试 fixture（录制的事件流）
├── .changeset/               # 版本与变更记录
├── pnpm-workspace.yaml
├── tsconfig.base.json        # 基础编译配置（各包 extends）
├── tsconfig.host.json        # 宿主侧（Node 运行时）
├── tsconfig.client.json      # 渲染侧（浏览器环境）
└── package.json
```

**硬性约定**（对应 [00 §5.1](./00-文档总览与全局约定.md)）：

| 约定 | 值 |
|---|---|
| npm scope | `@lcode/*`（组名不进包名：`packages/core/session` → `@lcode/session`） |
| 模块系统 | ESM only（`"type": "module"`） |
| 包间引用 | 用包名（`@lcode/fs`） |
| 包内相对引用 | **带 `.ts` 后缀**（`./impl.ts`） |
| 每个包 | 必须有 `README.md`、`package.json`、`src/`、`tsconfig.json` |
| README 内容 | 职责、API 摘要、事件、扩展点、`Known Limitations`（边界与不变量写在 [20](./20-模块设计与接口清单.md)，README 不重复） |

## 3. 环境与版本要求

| 项 | 要求 | 说明 |
|---|---|---|
| Node.js | **≥ 22.19**（推荐 22 LTS 或以上） | 依赖原生 `fetch`、`node:test` 之外的现代 API；ESM 行为一致 |
| pnpm | **≥ 9**，用 `packageManager` 字段锁定 | 必须是 pnpm（workspace 协议 + 严格依赖解析） |
| 操作系统 | macOS 13+ / Windows 11 / Linux（glibc 2.31+） | 三平台的沙箱机制不同，见 [12 §3](./12-安全权限与沙箱模型.md) |
| 必需工具 | `git`、`pnpm`；Windows 另需 PowerShell 7 | — |
| 可选工具 | `ripgrep`（搜索更快）、`wine`（仅用于诊断 Windows 专有失败） | 缺失时自动降级 |

```jsonc
// package.json（根）
{
  "engines": { "node": "^22.19 || >=24" },
  "packageManager": "pnpm@9.12.0"
}
```

> **不锁定 Node 到某个补丁版本。** 锁太死会让贡献者升级受阻；锁太松会出现"我这里能跑"。折中：`^22.19 || >=24`，并在 CI 上跑 22 与 24 两档。

## 4. 初始化：第一天就能跑起来

```bash
git clone <repo> && cd lcode
corepack enable                 # 启用 packageManager 声明的 pnpm
pnpm install                    # 安装全部 workspace 依赖
pnpm run build                  # 首次必须构建（部分包依赖产物）
pnpm run typecheck && pnpm test # 自检环境
pnpm run dev:desktop            # 起桌面应用（开发模式）
```

**验证环境是否正常**：

```bash
pnpm lcode --profile cli "用一句话自我介绍"   # 需要已配置模型（见下）
pnpm lcode doctor                             # 环境自检：Node / 沙箱 / 权限 / 模型连通性
```

**模型配置（首次）**：

```bash
cp .env.example .env            # 填入 DEEPSEEK_API_KEY 等（.env 不进 git）
pnpm lcode doctor --model       # 打印每个字段的生效值与来源层
```

> 注意：`doctor --model` 的输出必须与桌面端「设置 → 模型」页显示一致（`FR-MODEL-009`）。这是产品需求，不只是工程便利。

## 5. 常用命令一览

| 命令 | 作用 | 何时用 |
|---|---|---|
| `pnpm install` | 安装依赖 | 拉代码后、改依赖后 |
| `pnpm run build` | 全量构建（tsc 出类型 + 打包运行时） | 首次、改导出后、提交前 |
| `pnpm run dev:desktop` | 起 Electron 开发模式（HMR） | 日常开发 UI / 主进程 |
| `pnpm run dev:cli` | 起 CLI（源码直跑，watch 重启） | 日常开发内核 / 工具 |
| `pnpm run typecheck` | 全仓类型检查 | 提交前 |
| `pnpm run lint` | ESLint + 格式检查 | 提交前（pre-commit 自动跑） |
| `pnpm run format` | 自动格式化 | 保存时或提交前 |
| `pnpm test` | 单元 + 集成测试（vitest） | 高频 |
| `pnpm test:watch` | 监听模式 | 开发中 |
| `pnpm test:coverage` | 覆盖率（核心包逐文件 100%） | 提交前（CI 用同一命令） |
| `pnpm test:replay` | 快照重放（**无密钥可跑**） | 改了循环 / 提示词 / 工具后 |
| `pnpm test:e2e` | 真实模型（无密钥自动跳过） | 发布前、改适配器后 |
| `pnpm run check:invariants` | 七条不变量检查（I1–I7） | 提交前，CI 强制 |
| `pnpm run check:deps` | 依赖方向检查（[20 §3](./20-模块设计与接口清单.md#3-依赖规则谁可以依赖谁)） | 提交前，CI 强制 |
| `pnpm run check:docs` | 文档集校验（链接 / 原型 / 术语） | 改文档后 |
| `pnpm run clean` | 清理构建产物 | 排障 |
| `pnpm run bench` | 性能基准（启动 / 首 token / 万级事件滚动） | 发版前 |
| `pnpm lcode --dump-config` | 打印最终插件装配（含层级与来源） | 排查"配置没生效" |

## 6. TypeScript 配置策略

### 6.1 三层配置

```jsonc
// tsconfig.base.json —— 所有包 extends 它
{
  "compilerOptions": {
    "target": "ES2023",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "lib": ["ES2023"],
    "strict": true,
    "exactOptionalPropertyTypes": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "noEmitOnError": true
  }
}
```

| 配置文件 | 用途 | 关键差异 |
|---|---|---|
| `tsconfig.base.json` | 基础严格设置 | 不直接被包引用 |
| `tsconfig.host.json` | 宿主侧（Node 运行时：main 进程、CLI、全部 packages） | `lib` 含 DOM 之外的 Node 类型 |
| `tsconfig.client.json` | 渲染侧（浏览器环境：renderer） | 不出现 `node:*` 导入；`lib` 含 DOM |

**为什么分 host / client**：渲染进程里一句 `import fs from 'node:fs'` 会在运行期炸掉，但类型检查发现不了——除非把两边的 `lib` 与可用模块分开。这个分离是**编译期防线**。

### 6.2 类型纪律（会被 lint 拦）

| 规则 | 说明 | 例外 |
|---|---|---|
| 禁止 `any` | 用 `unknown` + 收窄 | 与第三方无类型 API 的边界，需 `// eslint-disable-next-line` + 理由注释 |
| 禁止非空断言 `!` | 用显式检查和早返回 | 测试代码 |
| 禁止 `as` 强制断言跨类型 | 用类型守卫 | 从 `unknown` 收窄时允许 |
| 导出类型必须显式标注返回类型 | 公开 API 不靠推断 | 局部变量 |
| 只读优先 | 参数用 `readonly`、集合用 `readonly T[]` | 需要变异的场景 |
| 字符串枚举优先于原生 enum | 落盘值必须是字符串字面量（可读、可重放） | — |
| 不可变数据 | 事件与规范值必须一次构造完成，不得后续修改 | 内部构建过程 |

### 6.3 品牌类型（Branded Types）

id、路径、token 数量这类"同是 string/number 但语义不同"的值，用品牌类型区分，避免传错参数：

```ts
export type SessionId = string & { readonly __brand: 'SessionId' }
export type AgentId   = string & { readonly __brand: 'AgentId' }
export type Seq       = number & { readonly __brand: 'Seq' }
```

品牌类型定义在 `@lcode/util`，**不重复定义**。

## 7. 代码规范

### 7.1 命名

| 对象 | 规范 | 例子 |
|---|---|---|
| 包名 | `@lcode/<kebab-case>` | `@lcode/agent-loop` |
| 目录 / 文件名 | `kebab-case.ts` | `session-service.ts` |
| 类型 / 接口 | `PascalCase`，**不加 `I` 前缀** | `FsService`（不是 `IFsService`） |
| 函数 / 变量 | `camelCase` | `deriveMessages` |
| 常量 | `SCREAMING_SNAKE_CASE` | `SCHEMA_VERSION` |
| **ctx key** | 单数 = 一个引擎/策略/存储；复数 = 注册表 | `ctx.fs`（一个）vs `ctx.agents`（多个） |
| **事件名** | `域/事件`，域用单数 | `tool/call`、`session/event`、`agent/status` |
| **错误码** | 前缀分类 + 编号（见 [21 §6](./21-接口契约与错误码总表.md)） | `ET_TIMEOUT` |
| React 组件 | `PascalCase.tsx` | `SessionStream.tsx` |
| 测试文件 | 与源文件同名 + `.test.ts` | `session-service.test.ts` |

### 7.2 模块内部结构（每个包统一）

```
packages/<group>/<pkg>/
├── README.md
├── package.json
├── tsconfig.json
└── src/
    ├── index.ts          # 唯一出口：只 re-export 公开 API
    ├── types.ts          # 公开类型（接口包里是主体）
    ├── events.ts         # 事件声明合并（若有）
    ├── <feature>.ts      # 具体实现，一文件一主题
    └── <feature>.test.ts # 就近放置单测
```

**只有 `index.ts` 可以对外。** 深层导入（`@lcode/fs/src/x.ts`）是违规的，由 lint 拦。

### 7.3 错误处理

| 规则 | 说明 |
|---|---|
| 一切失败都是**具名错误** | 用 `LcodeError`（[21 §6.1](./21-接口契约与错误码总表.md)），不 `throw new Error('failed')` |
| 区分**内部信息**与**用户可见文案** | `message` 可以技术化；`userMessage` 必须过术语黑名单（[19 §6.2](./19-原型与交互规格.md)） |
| **禁止吞异常** | 空 `catch {}` 一律违规；要么处理，要么包装后抛出 |
| 降级必须**显式且可观测** | 降级要落盘事件或发警告日志，不允许静默 |
| 权限相关一律 **fail-closed** | 无应答即拒绝（D11） |
| 异步操作必须可取消 | 长操作接受 `AbortSignal` |

### 7.4 日志

| 级别 | 用在哪 | 是否进用户可见区 |
|---|---|---|
| `error` | 无法继续的失败 | 是（错误条） |
| `warn` | 降级、重试、异常但可继续 | 是（轻提示） |
| `info` | 生命周期里程碑（启动、会话创建、发布） | 否（诊断面板） |
| `debug` | 排障细节 | 否 |
| `trace` | 逐 chunk / 逐事件 | 否（默认关闭） |

**硬性**：

1. **凭据值永不进日志**（含 `trace`），由日志序列化器对已注册凭据值做脱敏 + golden test 守住（`SEC-CRED-001`）。
2. 协议模式下 **stdout 即协议**，日志必须走 stderr（[13 §4](./13-插件SDK与协议设计.md)）。
3. 日志行必须带 `sessionId` / `agentId`（若有），否则排障时无法归因。

### 7.5 注释与 JSDoc

| 必须有 JSDoc | 内容要求 |
|---|---|
| 公开接口的每个方法 | 一句话职责 + `@param` + `@throws`（错误码） |
| 事件声明 | `@mode`（emit/waterfall/parallel/serial）+ payload 每个字段 `@param` |
| 不变量与微妙约束 | 用 `// 不变量：…` 标注，并注明违反后果 |
| 任何"看起来可以简化但不能"的代码 | 写明**为什么不能**（这是最有价值的注释） |

**禁止**：复述代码的注释（`// 增加计数`）；过期的 TODO 不写日期与 owner 的。

## 8. 质量门禁与 CI

### 8.1 门禁表

| # | 门禁 | 命令 | 阻断合并 | 触发条件 | 耗时预算 |
|---|---|---|---|---|---|
| G1 | 格式 | `pnpm run format --check` | 是 | 每次提交 | < 30s |
| G2 | 类型 | `pnpm run typecheck` | 是 | 每次提交 | < 3min |
| G3 | Lint | `pnpm run lint` | 是 | 每次提交 | < 1min |
| G4 | 单元 + 集成 | `pnpm test` | 是 | 每次提交 | < 5min |
| G5 | 覆盖率 | `pnpm test:coverage` | 是 | 每次提交 | < 8min |
| G6 | **不变量** | `pnpm run check:invariants` | 是 | 每次提交 | < 2min |
| G7 | **依赖方向** | `pnpm run check:deps` | 是 | 改了 import | < 30s |
| G8 | 快照重放 | `pnpm test:replay` | 是 | 改了循环 / 提示词 / 工具 | < 6min |
| G9 | 构建 + 冒烟 | `pnpm run build && pnpm run smoke` | 是 | 发版、改导出 | < 10min |
| G10 | 包体积 | `pnpm run check:size` | 是 | 发版 | < 2min |
| G11 | 文档集 | `pnpm run check:docs` | 是 | 改 `docs/` | < 30s |
| G12 | 许可证 + 漏洞 | `pnpm run check:deps --license --audit` | 是（高危阻断） | 每周 + 改依赖 | < 3min |
| G13 | 真实模型 e2e | `pnpm test:e2e` | 否（无密钥自动跳过） | 发布前 | 不定 |
| G14 | 性能回归 | `pnpm run bench` | 否（出报告） | 发布前 | < 15min |

### 8.2 覆盖率阶梯

| 范围 | 要求 | 理由 |
|---|---|---|
| `packages/core/*/src` | **逐文件 100%** | 地基类代码：早期正确几乎免费，后期补上等于重写 |
| 其余 `packages/**/src` | 行 ≥ 85%，分支 ≥ 75% | 维持合理信心 |
| `apps/**` | 行 ≥ 60% | UI 层测试性价比低，靠端到端与人工 |
| 豁免机制 | 不提供核心包覆盖率豁免 | 核心文件逐文件 100%，不允许静默降低 |

### 8.3 七条不变量（CI 强制）

| # | 不变量 | 检查方式 |
|---|---|---|
| I1 | 模型可见即可重放 | 断言 `request.system === assembleFromLog(log)` 且 `messages` 深等于 `deriveMessages(log)` |
| I2 | `seq` 连续无空洞 | 追加后校验 `0..n-1` |
| I3 | 配对完整 | 每个 `tool/call` 有配对 `tool/result` |
| I4 | surface replace 不越界 | 区间校验 |
| I5 | 事件无损 JSON | 拒绝 BigInt/函数/循环引用/NaN/undefined |
| I6 | 核心循环无业务分支 | AST 扫描 `core/agent-loop` 源码关键词黑名单 |
| I7 | 凭据值不泄漏 | 遍历日志 / 遥测 / 错误堆栈断言不出现 |

详见 [15 §2](./15-测试策略与质量门禁.md)。

## 9. 协作流程

### 9.1 分支与提交

| 项 | 规范 |
|---|---|
| 主分支 | `main` 始终可构建、可发布（trunk-based） |
| 特性分支 | `feat/<短描述>`、`fix/<短描述>`、`docs/<短描述>`、`refactor/<短描述>` |
| 提交信息 | **Conventional Commits**：`type(scope): subject` |
| type | `feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf` / `build` |
| scope | 包名（不带 `@lcode/`）或 `docs` / `ci` / `repo` |
| 长度 | subject ≤ 72 字符，祈使句，不带句号 |

```
feat(session): 支持按安全切点分叉
fix(tools): 修复 await 语义下审批无应答时的死锁
docs(design): 补模块设计与接口清单
```

### 9.2 PR 要求

| 项 | 要求 |
|---|---|
| 单一目的 | 一个 PR 只做一件事；重构与功能分开 |
| 描述 | 变更动机 / 影响的模块 / 验证方式（跑了哪些命令） |
| 证据 | **只报告跑过的命令**，不写"应该没问题" |
| 测试 | 行为变更必须带测试；bug 修复必须带复现测试 |
| 文档 | 改接口 → 更新 [20](./20-模块设计与接口清单.md)；改决策 → 加 [17 ADR](./17-架构决策记录ADR.md)；改文档 → 跑 G11 |
| 规模 | 超过 600 行有效改动建议拆分（自动生成的产物不计入） |

### 9.3 评审清单（评审人逐条）

- [ ] 有没有出现**新的"冻结"接口**？有则必须过 ADR。
- [ ] 依赖方向是否合规（消费包没 import 实现包）？
- [ ] 新失败路径是否有**具名错误码**与人话文案？
- [ ] 是否引入了**静默降级**或**吞异常**？
- [ ] 新能力是否需要审批接缝？有没有绕过？
- [ ] 事件 payload 变更是否同步了 [06](./06-会话事件日志与可重放设计.md) 与 [22 §5](./22-数据字典与DDL.md)？
- [ ] 是否给"为什么不能简化"留了注释？

## 10. 测试基建

### 10.1 目录与命名

```
fixtures/
├── sessions/                  # 录制的事件流（快照重放的输入）
│   └── <scenario>/events.jsonl
├── diffs/                     # 渲染快照期望输出
└── README.md                  # 每个 fixture 的来源与用途
```

### 10.2 录制与回放（无密钥可跑）

```bash
pnpm test:replay:record   # 用真实模型跑一遍，把事件流录成 fixture（需要密钥）
pnpm test:replay          # 用 llm-replay 适配器回放，断言事件流与渲染一致（不需要密钥）
```

**为什么这是性价比最高的一层**：不花钱、确定性强、覆盖真实场景。改循环/提示词/工具后必须跑。

### 10.3 真实模型 e2e

| 项 | 做法 |
|---|---|
| 触发 | 无 `DEEPSEEK_API_KEY` 时**自动跳过**（不失败） |
| 成本控制 | 用小模型、固定种子、限制 max tokens |
| 防 flaky | 重试有上限；断言**结构化字段**（用了哪个工具、退出码、错误码），不断言自然语言文本 |
| 何时必跑 | 发布前、改适配器后 |

### 10.4 测试数据脱敏

fixture 里的真实路径、用户名、密钥一律替换为占位符（`/Users/<user>/...`、`sk-<redacted>`）。**录制脚本自动脱敏**，不依赖人工检查。

## 11. 构建与产物

| 项 | 做法 |
|---|---|
| 类型产物 | `tsc` 输出 `lib/**/*.d.ts` + `declarationMap` |
| 运行时产物 | 打包为 ESM（`lib/index.js`），保留 `exports` 映射 |
| 源码直跑 | 开发态用 `tsx` 的 ESM 钩子（`node --import tsx/esm`），**不经过构建** |
| 子进程 | 配置类子进程跑构建后的 `lib/`（不能依赖源码直跑） |
| 包 `exports` | 只暴露 `"."`（单入口），不暴露 `./src/*` |
| 平台特定包 | 用 `os` / `cpu` 字段限制安装（如 `sandbox-macos` 仅在 darwin 安装） |
| 产物体积 | 记录基线，超阈值（默认 +10%）报警 |

> **一条纪律**：**公开包的产物必须是"构建后可独立运行"的**。`examples/` 与 `apps/` 的冒烟测试跑的是构建产物，不是源码——否则构建期的问题（丢文件、路径错、CJS 混入）永远发现不了。

## 12. 调试与诊断

| 场景 | 手段 |
|---|---|
| "我改的配置没生效" | `pnpm lcode --dump-config`（含层级与来源）；再 `--dump-config --json > wiring.json` 对比 |
| "模型连不上" | `pnpm lcode doctor --model`（打印每个字段的生效值与来源层） |
| "沙箱没拦住" | `pnpm lcode doctor --sandbox`（各平台自检 + 已知逃逸面提示） |
| "这一步它到底看到了什么" | 打开回放（P3）→ 选中该步 → 看三快照（system / 工具 / 消息） |
| "某个工具为什么被拒" | 该调用的"为什么"面板：经过哪些策略、谁批准、依据是什么 |
| "会话日志异常" | `pnpm lcode sessions verify <id>`（seq 连续性、配对完整性、surface 区间） |
| "崩溃后发生了什么" | 查看恢复摘要：丢弃了几条撕裂记录、补记了哪些合成事件 |
| "性能问题" | `pnpm run bench -- --profile`（启动 / 首 token / 万级事件滚动 / 内存） |
| "插件为什么不加载" | `pnpm lcode plugins diagnose <id>`（清单校验 + 权限声明 + 启动日志） |

**日志位置**：`<Lcode Home>/logs/`（见 [22 §2](./22-数据字典与DDL.md)）。默认保留 7 天，`debug` 级别需显式开启。

## 13. 版本与发布

| 项 | 做法 |
|---|---|
| 版本管理 | Changesets：每个 PR 带一个 `.changeset/*.md` 说明变更类型（major/minor/patch） |
| 语义化版本 | 破坏性 = major；新能力 = minor；修复 = patch。**接口包的破坏性变更必须 major** |
| 内部包 | `private: true` 的包不发布，但版本号同步递增（便于对齐） |
| 内测通道 | `canary`（每次合并 main 自动发）→ `beta`（手动打标）→ `stable` |
| 自动更新 | Electron 自动更新；**必须支持回滚到上一个 stable** |
| 崩溃上报 | 遥测**默认关闭**；开启后仅上报崩溃栈（不含会话内容与路径） |
| 发布检查单 | G9–G14 全绿 + 手工冒烟（三平台沙箱拦截 / 审批弹窗 / 主题切换 / 真机崩溃恢复） |

**发布前必须确认的一件事**：`16 风险登记册` 里"**用户是否真的想要可审计**"那条风险的验证状态。它决定的不是怎么发版，而是要不要继续投入（[02 §7.3](./02-竞品与市场分析.md)）。

## 14. v0.1 的包初始化顺序

按依赖顺序建包，**每建一个就能跑一个的测试**。不要一次铺开全部目录。

| 批次 | 包 | 里程碑产出 | 依赖 |
|---|---|---|---|
| ① 地基 | `util` → `core/scope` → `core/session`（内存实现） | 能 append 事件、`seq` 连续、I2/I5 通过 | 无 |
| ② 派生 | `session-persistence-jsonl` → `session-persistence-sqlite` → `core/system-prompt` | 会话能落盘、能重建（I1 起步） | ① |
| ③ 循环 | `llm`（接口 + `llm-replay`）→ `core/agent` → `core/agent-loop` | **无密钥也能跑通一次循环**（回放驱动） | ② |
| ④ 能力 | `llm-deepseek` → `settings` → `credentials` → `core/agent-default-model` | 能用真实模型跑一次对话 | ③ |
| ⑤ 工具 | `fs` + `fs-local` + `tool-fs` → `shell` + `shell-local` + `tool-shell` | 能读写文件、能跑命令 | ④ |
| ⑥ 治理 | `interaction/approval` + `permission-presets` → `sandbox` + 三平台实现 | 越界写入会问、能拦住 | ⑤ |
| ⑦ 前端 | `apps/cli` → `apps/desktop`（main → preload → renderer） | 能演示 8 分钟脚本 | ⑥ |
| ⑧ 加固 | `session-persistence` 崩溃恢复 + 回放 UI + 集束 | v0.1 出口标准 | ⑦ |

> **关键点：第 ③ 批就要能"无密钥跑通一次循环"。** `llm-replay` 先于真实适配器存在，意味着**整个循环的骨架可以在不花钱、不联网的情况下被完整测试**。这是 [15 §3](./15-测试策略与质量门禁.md) 快照重放策略能成立的前提，也是排期上最容易被忽略、却最值钱的一步。

## 15. 我们不做什么

- **不做自定义构建系统**：用 pnpm + tsc + 现成打包器，不写自研 bundler。
- **不做 monorepo 自研依赖校验**：用现成工具 + 一个薄脚本。
- **不追求 100% 覆盖率**：只有核心包逐文件 100%（那里正确性最便宜），UI 层不追求。
- **不做"提交即发布"**：canary 自动发，stable 必须手动打标 + 走发布检查单。
- **不在仓库里存凭据**：`.env` 与任何密钥文件在 `.gitignore` 中；CI 用 secret 注入。
- **不引入需要联网才能跑的单元测试**：默认测试必须离线可过。

## 未决问题

- [ ] **是否引入 Turborepo / Nx 做任务编排**：当前用 pnpm 原生脚本 + 并发。包数超过 ~40 后可能需要缓存与依赖图调度。→ 由工程效率在 v0.2 前评估。
- [ ] **`apps/desktop` 的渲染构建链**：Vite 已定（D3），但 HMR 与主进程热重载的组合方式需要试验后固化。
- [ ] **覆盖率 100% 的分支口径**：`exactOptionalPropertyTypes` + `noUncheckedIndexedAccess` 会产生难以覆盖的防御分支。需要明确"哪些防御分支可豁免"的判据，否则会出现为凑覆盖率写测试。→ 由测试 owner 出判据。
- [ ] **fixture 的体量与保留**：录制的事件流会随场景增长。需要定上限与清理策略（与 [22 §9](./22-数据字典与DDL.md) 的容量策略对齐）。
- [ ] **Windows 上 PTY 的测试策略**：`terminal-pty` 在 Windows 上的行为依赖 ConPTY，CI 覆盖方式待定。
- [ ] **`check:invariants` 的 I6（AST 扫描）实现细节**：关键词黑名单会误伤注释与字符串。需要明确是"扫 AST 节点"还是"扫源码 + 排除注释"，以及白名单机制。
