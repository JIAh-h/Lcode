# 30 · 统一插件加载器设计草案（内置能力与第三方插件同一套内核）

> 状态：**草案，待评审**。本文只定形状与边界，不包含实施排期。
> 前置：[13 插件SDK与协议设计](./13-插件SDK与协议设计.md)、[20 模块设计与接口清单](./20-模块设计与接口清单.md)。

## 1. 问题：现在有两套插件机制

Lcode 的"一切皆插件"目前只对**第三方**成立：

| | 内置能力 | 第三方插件 |
|---|---|---|
| 形态 | `InternalBundleEntry`（编译期） | `lcode.json` + utility process（运行期） |
| 声明 | `{ id, provides, requires, adopts, mount }` | `{ id, name, version, entry, activation, permissions, contributes }` |
| 生命周期 | 进程启动时 `mount()`，退出时 `dispose()` | `activate` / `deactivate`，有状态机 |
| 能力范围 | 全部 `ctx`（直接调用） | 白名单 RPC（`ctx/registerTool` 等 3 个） |
| 能否禁用 | **否**（写死在组合里） | 是 |
| 能否替换 | 否 | 是（装另一个） |

**后果**（用户原话）：

> 第三方插件开发出来差异巨大，而且无法快速在产品中生效。

具体差异：

1. **API 不同**：内置插件用 `ctx.get('tools').register(...)`；第三方插件用 `host.request('ctx/registerTool', ...)`，参数形状不同。
2. **能力不同**：内置能注册 `systemPrompt.context(fn)`（动态、按会话）；第三方只能注册静态字符串 `promptSection`。
3. **优先级不同**：内置能力是"必然存在"的，第三方是"可选增强"——同一件事在两套体系里不等价。

## 2. 目标（按优先级）

| # | 目标 | 判定方式 |
|---|---|---|
| G1 | **API 一致**：一个能力插件，改成内置或第三方，业务代码不变 | 同一个插件包能同时以两种方式挂载 |
| G2 | **内置能力可禁用/可替换** | 配置里关掉某个内置条目，行为等同它不存在 |
| G3 | **依赖在装配期检查** | 缺依赖时报错在启动阶段，而不是运行时崩 |
| G4 | （可选）开发态热重载 | 只影响 DX，不影响生产装配 |

**非目标**：进程内热替换生产插件、跨进程状态迁移、Cordis 式的 fiber 自动回收。

## 3. 核心设计：一个加载器、两种宿主

```
                        ┌────────────────────────────────┐
                        │  PluginLoader（唯一装配入口）   │
                        │  - 读 manifest / bundle 声明    │
                        │  - 依赖解析 + 拓扑排序          │
                        │  - 生命周期编排                 │
                        └───────────────┬────────────────┘
                    ┌───────────────────┴───────────────────┐
                    ▼                                       ▼
        ┌───────────────────────┐              ┌───────────────────────┐
        │ InProcessHost（内置）  │              │ ProcessHost（第三方）  │
        │ - 直接持有 ctx         │              │ - utility process      │
        │ - 同步调用             │              │ - RPC 代理（异步）      │
        └───────────────────────┘              └───────────────────────┘
                    │                                       │
                    └────────── 同一份 PluginApi ───────────┘
```

**关键约束**：`PluginApi` 必须是**异步友好**的（内置侧直接返回 Promise，第三方侧走 RPC），否则两套 API 无法共用。

### 3.1 PluginApi（统一的插件接口）

```ts
/** 插件能看到的全部能力。内置与第三方共用这一份形状。 */
export interface PluginApi {
  readonly id: string
  readonly version: string
  /** 插件声明的配置（已按 configSchema 校验） */
  readonly config: unknown

  // ── 能力注册（返回 Disposer，卸装时自动撤销）──
  registerTool(spec: PluginToolSpec): Disposer
  registerPromptSection(input: PromptSectionSpec): Disposer
  registerListener(event: string, handler: PluginListener): Disposer

  // ── 只读查询（不产生副作用）──
  /** 当前会话的工作区（由宿主注入，插件不可伪造） */
  workspaceOf(sessionId: string): string | undefined
  /** 受 manifest.permissions 约束的文件读写 */
  readonly fs: PluginFs
  /** 结构化日志，落 `~/.lcode/logs/plugin/<id>.log` */
  log(level: 'info' | 'warn' | 'error', message: string): void
}

/** 提示词片段：支持静态与动态两种 */
export type PromptSectionSpec =
  | { readonly id: string; readonly content: string; readonly order?: number }
  /** 内置插件可用动态形态；第三方插件降级为静态（见 §5.2） */
  | { readonly id: string; readonly render: (ctx: AssembleContext) => string; readonly order?: number }
```

### 3.2 两种 Host 的差异收敛

| 能力 | InProcessHost | ProcessHost | 统一语义 |
|---|---|---|---|
| `registerTool` | 直接 `tools.register` | RPC + 代理 | 都返回 `Disposer` |
| `registerPromptSection` 静态 | 支持 | 支持 | ✅ 一致 |
| `registerPromptSection` 动态 | 支持（`render(fn)`） | **不支持**（降级为静态或拒绝） | ⚠️ 见 §5.2 |
| `registerListener` | 支持 | 支持（已实现） | ✅ 一致 |
| `workspaceOf` | 直接读 | RPC 同步**不可行** → 改为主机推送 `session/workspace` 事件 | ⚠️ 见 §5.3 |
| `fs` | 直接调用 | RPC | 异步一致 |
| `log` | 写文件 | RPC | 一致 |

## 4. 声明形状统一

### 4.1 现状对比

```ts
// 内置（InternalBundleEntry）
{ id, provides, requires, adopts, mount(ctx) }

// 第三方（PluginManifest）
{ id, name, version, entry, activation, permissions, contributes, configSchema }
```

### 4.2 统一后的形状

**保留两个交付物，但字段对齐**：

```ts
/** 共同字段：两种插件都必须有 */
export interface PluginDescriptor {
  readonly id: string
  readonly name: string
  readonly version: string
  /** 依赖的服务名；装配期拓扑排序 + 缺失即报错（G3） */
  readonly requires: readonly string[]
  /** 提供的服务名（内置必需；第三方通过 RPC 提供，可选） */
  readonly provides: readonly string[]
  /** 声明式贡献：加载器据此校验"注册的东西是否声明过" */
  readonly contributes: {
    readonly tools?: readonly string[]
    readonly promptSections?: readonly string[]
    readonly events?: readonly string[]
  }
}

/** 内置插件：多一个 mount */
export interface BuiltinPlugin extends PluginDescriptor {
  readonly kind: 'builtin'
  readonly mount: (api: PluginApi) => RuntimeDisposer | Promise<RuntimeDisposer>
}

/** 第三方插件：多 entry / permissions / configSchema */
export interface ExternalPlugin extends PluginDescriptor {
  readonly kind: 'external'
  readonly entry: string
  readonly permissions: PluginPermissions
  readonly configSchema?: JsonValue
}
```

**兼容策略**：`InternalBundleEntry` 保留为**内部类型**（装配层用），`BuiltinPlugin` 是它的**对外投影**。这样不破坏现有 97 个包，但公开的插件 API 只有一套。

## 5. 三个需要决策的难点

### 5.1 依赖解析：拓扑排序（**已具备**）

**更正**：早期草案写"`requires` 字段存在但没有被使用"，这是错的。
`composeRuntimeProfile`（`packages/core/runtime-composition`）**已经实现**：

| 已有能力 | 位置 |
|---|---|
| `requires` 缺失检查（装配期抛 `EC_COMPOSITION_MISSING`） | `index.ts:88-99` |
| 拓扑排序（按 `provides` 满足 `requires`，Kahn 式逐轮挑选） | `index.ts:101-128` |
| 循环依赖检测（无可选条目时抛 `EC_COMPOSITION_MISSING`） | `index.ts:109-112` |
| `provides` 重复注册检查 | `index.ts:68-85` |
| mount 后校验服务确实注册（`EC_COMPOSITION_PROVIDER`） | `index.ts:121-126` |
| 逆序 dispose（失败时先回滚已挂载条目） | `index.ts:129-132, 153-161` |

**所以 P3 不需要新建机制**，只需确认第三方插件介入后仍走这条装配路径。

**剩余风险**：现有条目可能存在**隐式依赖**（A 的 mount 里 `ctx.get('x')`，但 A 没声明
`requires: ['x']`）。拓扑排序只看声明，所以这种依赖靠"声明顺序碰巧正确"在跑。
统一加载器落地前应该跑一次"声明补齐"——把所有 `ctx.get('x')` 反查成 `requires`。

### 5.2 动态 promptSection：第三方怎么办？

这是最硬的约束：`isPromptSection` 要求 `content: string`，而 `systemPrompt.context(fn)` 支持函数。

**三个选项**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 第三方插件**不支持**动态 promptSection，需要在 manifest 里声明 `contributes.dynamicPrompt: true` 才能装 | 明确限制，不误导开发者 |
| B | 允许第三方声明，但**只在会话启动时求值一次**（异步 RPC） | 语义与内置不同（不是每步重算） |
| C | 改 `systemPrompt.context` 支持异步 | 装配链路大改，风险高 |

**选 A**：能力边界诚实，比"看起来能但行为不同"好。

### 5.3 `workspaceOf` 跨进程怎么给？

第三方插件在独立进程，同步查询工作区不可能。

**建议**：宿主在会话开始时**推送** `session/workspace` 事件，插件自己缓存。

```ts
api.registerListener('session/workspace', ({ sessionId, workspace }) => { ... })
```

**代价**：插件要在事件到达前处理"还不知道工作区"的情况。文档里明确要求。

## 6. 创造模式：让模型造出"能装上"的插件

这是本文最容易被漏掉、但决定成败的一环：**插件大多是模型造的**。加载器再统一，如果没有一份"造插件时必须遵守的标准"，模型产出的插件照样接不进来。

DSH 的做法值得直接借鉴，但要注意它的教训。

### 6.1 DSH 的创造模式：三个 Skill + 渐进式披露

DSH 把造插件的知识做成**三个 skill**，而不是塞进系统提示词：

| Skill | 职责 |
|---|---|
| `cordis-plugin-development` | 流程 + 知识来源顺序 + 索引表 |
| `cordis-composition-reference` | Loader patch 方言 + 可加载插件包清单 |
| `editing-cordis-compositions` | 组合编辑配方 |

**关键设计（DSH 自己踩过坑后改的）**：

| 坑 | 他们原本怎么做 | 改成了什么 |
|---|---|---|
| **单文件太大** | 一个 8.7 KB 的 SKILL.md 塞了三个互斥配方 | 拆成 `SKILL.md`（流程）+ `references/`（配方）+ `templates/`（可复制模板） |
| **超过修剪阈值** | 8.7 KB > 工具结果保留头尾的 8192 字符阈值 | 首屏压到 3.9 KB，配方按需加载 1~3 KB |
| **禁止读源码** | 两个 skill 都禁止读源码，skill 文本成了唯一知识来源 | **改成有序的知识来源**：先查 `cordis_inspect_query` → 再读包 README → 最后读源码 |

**最有价值的一条**：DSH 明确写了**取证顺序**，而不是禁读：

```
① 当前项目及已安装包的 package.json / exports / types / README
② 环境提供的 checkout（只读分析）
③ 克隆官方仓库取证（明确 tag/commit）
④ 仍不足时，选可安全失败的最小实现并标注假设
```

为什么重要：**框架 API 会漂移**，写死在 skill 里的知识一定会过期。教模型"怎么查"比"告诉它答案"可靠。

### 6.2 Lcode 的现状

| 已有 | 缺 |
|---|---|
| ✅ `skill-creator` 技能（教怎么造**技能**） | ❌ 教怎么造**插件**的技能 |
| ✅ 技能渐进式加载（先读 name/description，必要时读全文） | ❌ 插件的 `manifest` / `PluginApi` 用法文档 |
| ✅ `references/` / `scripts/` / `assets/` 目录约定 | ❌ 可复制的插件模板 |

**结论**：需要新增一个 `lcode-plugin-creator` 技能，与 `skill-creator` 并列。

### 6.3 `lcode-plugin-creator` 的结构（对齐 DSH）

```
resources/skills/lcode-plugin-creator/
├── SKILL.md                     流程 + 知识来源顺序 + 索引（≤ 4000 字符）
├── references/
│   ├── plugin-api.md            PluginApi 逐方法说明 + 示例
│   ├── manifest.md              lcode.json 字段与校验规则
│   ├── lifecycle.md             activate/deactivate/dispose 的时序
│   └── verification.md          怎么验证"这个插件真能装上"
└── templates/
    ├── tool-plugin/             最小工具插件（能直接 npm pack）
    ├── prompt-plugin/           注入提示词的插件
    └── service-plugin/          提供服务的插件（若支持）
```

**SKILL.md 内容骨架**（首屏必须够用）：

```markdown
---
name: lcode-plugin-creator
description: 创建 Lcode 插件（工具 / 提示词片段 / 事件监听）。当用户要求"造一个插件""扩展 Lcode 能力""写个自定义工具"时使用。
---

## 1. 先判断形态
- 只是一个可复用的提示词/流程 → 用 `skill-creator` 造**技能**，不是插件
- 需要调用本地能力（文件/网络/命令） → 造**插件**
- 不确定 → 先问用户

## 2. 取证顺序（不要猜 API）
① 读 `~/.lcode/plugins/` 下已装插件的 `lcode.json` 与 `src/`
② 读本项目 `packages/extension/plugin-sdk/src/`（若可见）
③ 读 `docs/13-插件SDK与协议设计.md`
④ 仍不确定：选最小可运行实现，并在 README 标注假设

## 3. 走模板，不要从零写
复制 `templates/tool-plugin/`，改 `lcode.json` 的 id/name 和 `src/index.ts`。

## 4. 必须满足的四条（否则装不上）
1. `lcode.json` 的 `contributes.tools` 必须列出你注册的每个工具名
2. 每个工具必须在 `activate` 里通过 `ctx.registerTool` 注册
3. 所有资源必须返回 disposer
4. `entry` 指向的文件必须存在且能被 Node 加载

## 5. 验证
见 `references/verification.md`。**不要只跑 typecheck 就说"能装上"。**
```

### 6.4 关键约束：创造模式产物的**可验证性**

DSH 的验证矩阵给了一个重要启发：**"能装上"必须可自动判定**，不能靠模型自我感觉。

Lcode 应该提供：

| 检查项 | 怎么做 |
|---|---|
| manifest 合法 | 已有 `parsePluginManifest` |
| `contributes` 与实际注册一致 | 加载时校验（**这个现在没有，要补**） |
| `entry` 可加载 | 尝试 `import()` |
| disposer 完整 | 卸载后检查注册表回到初始状态 |
| 端到端 | 装进临时 profile → 启动 → 断言工具出现 |

最后一条对应 DSH 的"从零安装验证"：**不要只测单元，要真的装一遍**。

### 6.5 与加载器的关系

```
创造模式（skill）
    ↓ 产出一个符合标准的产品
lcode.json + src/index.ts
    ↓ 被同一个加载器接管
PluginLoader → InProcessHost / ProcessHost
```

**没有创造模式的标准，加载器只是空壳**——模型会按自己的理解写插件，然后发现装不上。

## 7. 实施顺序（建议）

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P0** | 写 `lcode-plugin-creator` skill + 三个模板 + 验证清单 | **模型能造出符合标准的插件**（先于加载器，因为它是标准本身） |
| **P1** | ~~定义 `PluginApi` / `PluginDescriptor`~~ **改为扩展现有 `InternalBundleEntry`**：它已有 id/provides/requires/adopts/mount，与 PluginDescriptor 形状一致，无需新造一套 | 内置与第三方用同一个 entry 形状 |
| **P2** | 内置插件支持禁用/替换（G2）—— **已实现**：`applyBundleFilter` 读 `plugins.disabled` 在装配前过滤 | 配置里能关掉某个内置条目 |
| **P3** | ~~依赖拓扑排序（G3）~~ **已具备**（`composeRuntimeProfile`），且已验证第三方插件也走这条路径 | 缺依赖在启动时报错 |
| **P4** | 第三方插件适配到统一装配路径 —— **已实现**：每个已启用插件生成 `plugin:<id>@<ver>` bundle entry，mount 即 `lifecycleService.activate`；provides 留空（不提供 ctx 服务，避免跨进程依赖），requires 固定五项宿主服务；**client-only 插件 activate 跳过 host 启动**（沙箱下必超时，实测 75ms vs 26s） | 两者走同一次 `composeRuntimeProfile`（G1 的装配层达成） |
| **P5（可选）** | 开发态热重载 | DX 提升 |

**P4 落地后的状态**：第三方插件与内置能力在同一个 `composeRuntimeProfile` 里拓扑排序；
`plugins.disabled` 同时管两类（第三方条目的 id 是 `plugin:<id>@<version>`）；
坏插件 activate 失败降级为告警，不炸应用（与内置 bundle 相反——内置是产品承诺，第三方不是）。
G1（API 一致）的**装配层**已达成；**能力面**（host RPC vs 进程内 ctx）差异保留，这是执行位置决定的，见 §3。

**P0 必须在 P1 之前**：先把"标准"写下来（skill 是标准最好的载体），再让加载器去实现它。否则会先写出一堆实现细节，再回头补文档，两头对不上。

**P1-P3 是"让内置能力真正可插拔"，P4 是"让第三方和内置对齐"。**

## 7. 明确不做（与 Cordis 的分界）

| Cordis 有 | 我们不做 | 理由 |
|---|---|---|
| fiber 状态机 + 自动回收所有 effect | 不做 | 现有 `Disposer` 模式已够；自动回收要求插件必须用 `ctx.effect` 包装，反而增加心智负担 |
| 依赖是活的（provider 换 → 依赖者重载） | 不做 | 与"装配确定性"冲突；我们只在启动时装配一次 |
| 热重载改变监听器顺序 | 不做 | 我们的策略层依赖固定顺序（`waterfall` 的首个决定） |
| 配置即装配（连内核都可替换） | **部分做** | 内置能力可禁用（G2），但内核服务（session/tools/llm）仍是固定装配 |

**一句话**：借 Cordis 的"声明 + 生命周期"形状，不借它的"运行时替换"复杂度。

**关于创造模式**：借 DSH 的"**skill 承载标准 + 渐进式披露 + 有序取证**"，但**不做**它的"禁止读源码"（那是他们的临时折中，后来也改成了有序来源）。

## 9. 界面扩展（client 插件）——已实现

### 9.1 缺口是什么

原设计里插件只有 host 一半：工具、提示词、事件监听。它跑在独立 utility process 里，
**拿不到渲染层**。后果是"换皮肤 / 加面板 / 改界面"这类需求，插件体系一个都做不了，
只能去改应用源码——那等于插件体系缺了一整块。

真实触发场景：用户在创造模式下问"能不能做一个换肤插件"，模型逐条核查协议后
给出了正确结论（做不了），然后建议直接改源码。**答案是对的，但产品方向是错的。**

### 9.2 做法

新增 `contributes.client`（`entry` + `slots`），插件可以多一个渲染层入口：

```
插件进程（host）      渲染进程（client）
工具/提示词/事件   ←→  界面/主题/面板
```

| 决策 | 选择 | 理由 |
|---|---|---|
| 交付方式 | 主进程读源码 → IPC → 渲染层 `import()` | 渲染进程 dev 走 http、生产走 `file://`，而插件在 `~/.lcode/plugins/` 下，两种协议下 import 绝对路径都会被拦 |
| 加载通道 | Blob URL 优先，`data:` URL 兜底 | Blob 继承文档 origin，某些组合会被拦；`data:` 不继承 origin。插件要求单文件，正好不受"data: 内无相对 import"的限制 |
| 插件接口 | 渲染函数 + `api.h()`，不给 React | 插件代码是外部来源，不给它组件树访问权，能做什 么由 API 明确划定 |
| 插槽 | 枚举（theme / sidebar.bottom / conversation.top / settings.section） | 插槽是宿主给的挂载点，插件不能凭空创造位置 |
| 样式修改 | 只放行 `--*` 自定义属性 | 改具体属性会绕过设计令牌体系，得到"一半暗一半亮" |
| 背景图 | 只接受 `https:` / `data:image/` | `file:` 会让插件变成本机文件探测器 |
| 元素标签 | 拦 `script`/`iframe`/`object`/`style` 等 | 否则插件重新获得任意执行能力，绕开 API 边界 |
| 生命周期 | 与 host 半**独立** | `state` 反映的是 host 激活结果；两者绑一起会让"host 起不来但界面能用"的插件整体失效 |

### 9.3 host 插件激活超时 —— **已解决：改为宿主进程内加载**

**结论先说**：插件不再起独立子进程，改为在宿主进程里 `import`（见 §9.6）。激活耗时
**26 秒超时 → 8 毫秒**，工具能注册、能调用、`plugin_verify` 能通过。

下面是完整排查经过，留着避免重复踩。

#### 症状

`rt.plugins.activate()` 调 `createPluginHost` 时，`host/initialize` 一直超时（约 26 秒）。
任何带工具/提示词/事件订阅的插件都这样；纯 client 插件不受影响（它不启动宿主进程）。

#### 逐层排查

| 验证 | 结果 |
|---|---|
| 沙箱 helper `--probe` | ✅ 四项全 true |
| 手工 `--run -- node -e "…"` | ✅ 正常输出 |
| 手工 `--run -- node <脚本.mjs>` | ❌ `EPERM: lstat 'D:\'`（Node 对驱动器根做 `realpath`） |
| 沙箱里 `whoami /groups` | ⚠️ **`Low Mandatory Level`**（正常进程是 Medium） |

#### 真正的根因

APPContainer 模式下 helper 把子进程降到 **Low 完整性级别**——它连驱动器根都 `lstat` 不了，
而 Node 执行**脚本文件**时必须 realpath 整条路径。`node -e`（内联代码）不解析文件路径，
所以能跑；这正是"看起来沙箱正常、实际插件起不来"的原因。

#### 试过但无效的方案（不要重复踩）

| 方案 | 结果 |
|---|---|
| 主进程设 `process.env.ELECTRON_RUN_AS_NODE = '1'` | ❌ Electron 内部 network service 也按 Node 模式起，崩溃重启，应用不可用 |
| 对插件目录单独 `wrap` 做 ACL `--prepare` | ❌ 无效 |
| 给 Node 目录做 `--prepare` | ❌ `无法授予工作区 ACL（拒绝访问）`——需管理员权限 |
| 改 `PATH`（合并注册表 + nvm） | ❌ PATH 里有也白搭：目录读不了 |
| 换成 Job Object（`danger-full-access`，去掉 AppContainer） | ⚠️ 有改善但没解决：26s → 4.3s 退出，**完整性降级仍在** |

#### 最终解法

**放弃进程隔离，插件在宿主进程内 `import`**——与 DSH 的 Cordis 完全一致。
详细理由与安全模型见 §9.6。

### 9.4 还没做

| 项 | 现状 |
|---|---|
| 面板类插件的样式基线 | 只给了插槽，没给插件可用的样式类名，面板会显得"不像 Lcode" |
| 客户端插件市场/启用开关 UI | 设置页已能列出插件与启停；client 半随启用状态自动加载 |
| 主题持久化 | `app:get-theme` 仍硬编码返回 `light`；插件设的变量重启后要重新渲染（本来就会，因为插件每次启动都跑） |
| 插槽热重载 | 改插件 client 入口需重启应用 |

### 9.5 已修的附带问题：settings 双写不同步

**症状**：`settings_kv` 是 `settings.json` 的投影，但只在 `open()` 同步一次。
用户手改文件后读到的仍是旧值，且来源标注"settings.json"——实测导致
"测试脚本恢复了 JSON，但被删除的禁用配置复活"。

**修复**：`LocalSettingsService.refreshFromDisk()`——每次读（`ensureOpen`）对比
文件 mtime，变化才重建 L4 投影（先清旧 L4 条目再重灌，L2/L3 与内存层不受影响）。
mtime 未变则零 DB 开销。

**边界**：这解决"读到手改值"；`settings.set()` 写路径本来就是"内存→文件+表"双向，
不存在此问题。

### 9.6 插件改为宿主进程内加载（与 DSH 同构）

**决定**：插件不再起独立 utility process，改为在宿主进程里 `import`。

#### 为什么

§9.3 的排查证明：AppContainer（及 Job Object 下的完整性降级）会让 **Node 无法执行脚本文件**。
而"安全"与"能跑"在这里必须选一个——DSH 的选择很明确：

> 官方沙箱文档：「**Only a confined execution** reaches `ctx.sandbox`」

沙箱只约束**模型执行的命令**（shell/bash），**不约束插件自身的加载**。插件是宿主进程里的
模块（Cordis `apply(ctx)`），安全由声明式能力与权限模型保证，不由进程隔离保证。

#### 安全模型（替代进程隔离）

| 层 | 保证什么 |
|---|---|
| **能力边界** | 插件只能调用 `ctx` 提供的方法：`registerTool` / `registerPromptSection` / `on` / `request`；没有 `fs`、没有 `subprocess`、没有 `process` |
| **声明核对** | manifest 的 `contributes.tools` / `promptSections` 未声明的注册**直接抛错**（`EX_UNDECLARED_PERMISSION`） |
| **权限白名单** | `permissions` 决定 `capabilities` 快照；插件拿到的是只读目录，不满足的调用由宿主拒绝 |
| **异常隔离** | `activate`、每次工具执行、每个事件回调**全部包 try/catch**：异常转成错误返回，不外泄到进程顶层 |

#### 代价（与 DSH 相同）

插件与主进程同进程。一个死循环或 `process.exit()` 仍能拖垮应用——但 DSH 接受同样的风险，
因为收益（插件能真正工作）远大于此。

#### 实测收益

| 指标 | 子进程 + AppContainer | 宿主进程内 |
|---|---|---|
| 激活耗时 | 26s 超时 | **8ms** |
| 工具注册 | ❌ | ✅ |
| 工具调用 | ❌ | ✅ |
| `plugin_verify` | `inconclusive` | **`passed: true`** |

#### 保留了什么

`utility-runner.mjs` 与 `createPluginHost`（子进程宿主）**保留未删**：将来若沙箱能解决
完整性降级（需重编 native），可切回去。当前 `startHost` 指向进程内实现。

### 9.7 插件资源与自建路由（对齐 DSH 的 webServer）

**背景**：换肤插件需要用本机图片/视频当背景。调查 DSH 发现：它的
`/plugins/<pkg>/assets/` 静态资源路由**只放行图片**（`.svg/.png/.webp/.jpg/.jpeg`）；
视频皮肤插件（如 `dsh-video-skin`）靠**自己注册 HTTP 路由**
（`/dsh-video-skin/background.mp4`，带 Range）提供视频。即：**平台只给入口，资源由插件伺服**。

Lcode 照此实现两层：

| 层 | 形状 | 说明 |
|---|---|---|
| 静态资源 | `lcode-plugin://<id>/<包内路径>` | 主进程协议；只放行媒体扩展名（图片/视频/字体），只限插件自己目录；`nosniff` + `etag`（304）+ 未启用插件 404 |
| 自建路由 | `ctx.registerRoute(path, handler)` | manifest 需声明 `contributes.routes`；协议分发**先查路由**，未命中才落静态资源；handler 收 `{method,url,headers}`，返回 `{status,body,headers}`（body 为字符串） |

**路由安全规则**（与工具/提示段同一套"声明才能注册"）：

1. 未在 `contributes.routes` 声明的路径，注册时抛 `EX_UNDECLARED_PERMISSION`；
2. 路由按插件隔离（A 的路由 B 命中不了），最长前缀优先，随插件卸载撤销；
3. 路径规范化拒绝 `..` 与 `//host` 协议相对写法。

**实测收益**：视频背景不再需要平台加白名单——插件自建路由即可（Range/鉴权/按需生成
都行）。端到端验证：插件注册 `/wallpaper` → `lcode-plugin://acme.route/wallpaper/bg.mp4`
命中 → 200 响应。

**顺带的客户端接口**：`setBackgroundMedia`（图片+视频，替代只有图片的
`setBackgroundImage`，旧接口保留兼容）。非法 URL **抛错**而非静默丢弃——静默丢弃
曾让"皮肤没生效"极难排查。

### 9.8 启停为什么必须重启，以及两处状态判据的修正

**结论：插件启停一律走重启，不做热重载。**

一开始做的是热重载（停用后重新拉一遍 client bundle），实测两条路都不通：

| 半边 | 热重载为何不成立 |
|---|---|
| **host**（工具/提示段/事件） | 这些是在**装配期**挂进注册表的。运行中激活只会让 lifecycle 记录出现，`tools.schemas()` 数量**不变**——界面显示"已启动"但模型用不了它的工具 |
| **client**（主题/面板） | 插件若自带 `MutationObserver`（皮肤类几乎都会），宿主清掉的副作用会被它**立刻加回来**，观感上"停用没生效" |

所以最终改为：宿主在安装/启停/卸载时广播 `lcode:plugins.changed`，界面据此显示
「重启刷新」按钮；`app.relaunch({ args: process.argv.slice(1) })` 保留启动参数
（不带参数会启动一个空 Electron → 白屏）。

**沉淀的判断法**：判断"某改动要不要重启"，先看它的注册发生在**装配期**还是**运行期**。
装配期的只能重启；运行期的才有热更新可能。当第三方代码自带副作用恢复机制时，
宿主侧清理不可靠——此时应如实告知用户要重启，而不是做半灵不灵的热重载。

**同批修的两个状态判据**：

1. `PluginLifecycleManager.inspect()` 原本要求 `state === 'active' && host !== undefined`。
   纯客户端插件**根本没有 host**，于是永远不出现在 `inspect()` 里——设置页那行一直
   显示"未启动"，点"启动"又提示"已启动"，两处说法矛盾。改为只看 `state`，
   无 host 时 `capabilities` 用空集。
2. `clientBundles` 的注释写着"只排除被用户停用的插件"，但代码里**漏了这个判断**，
   停用的插件照旧源码下发、重载后又加载回来。补 `state !== 'enabled'` 才真正生效。

**另外**：`LocalPluginRegistry` 原先把 `openIndexDb()` 的结果缓存在实例上，
任何一次 `closeIndexDb()`（索引重建、`sessions.close()`、测试清理都会）之后
这个实例就永久失效，之后每次查询都抛 `The database connection is not open`——
实测表现为"一打开设置页的插件模块就报错"。改成 getter 每次现取（`openIndexDb`
自带连接缓存且对已关闭的会重开），天然自愈。

### 9.9 会话历史分页：按 turn 切 + 剔除流式增量

长会话切换慢的根因不在渲染，而在**传输**。实测一个会话：

```
21.2 MB | 84,795 条事件 | 实测只有 12 轮 / 334 条消息
其中 assistant/chunk = 82,636 条（97% 条数，69% 体积）
```

**光加"轮数窗口"对它几乎无效**（12 轮全在 40 轮窗口内）。两层收紧：

1. **按 turn 边界切片**（`sliceEventsByTurns`）。不能按事件条数硬切——那会把某一轮
   劈成两半，`turn/start` 在前页、`turn/end` 在后页，界面会一直显示"正在执行"。
   实测两页的 `turn/start` 与 `turn/end` 数量始终相等。
2. **剔除 `assistant/chunk`**（`stripStreamChunks`）。这些增量只服务于"正在生成"时的
   逐字渲染，最终内容完整存在于 `assistant/message`。**只剔除历史分页路径**，实时推送
   那条链路不能动。21.2 MB → 5.6 MB。

首屏 40 轮、每次"加载更早"追加 20 轮，合并时按 `seq` 去重。

**顺带**：diff 的 `meta.hunks` 占 diff 相关体积 85%（147KB/173KB），改为首屏只下发
`changes`（文件名+增删数），悬停某个文件时才用 `session.diff` 按 seq 取逐行内容。

**沉淀的原则**：性能优化先测量数据构成、再调参数（先按"对齐首屏条数"改，收益远小于
直接定位到占 69% 的流式增量）；持续输出类数据（增量、日志分片）的生命周期只属于
"正在生成"那一刻，不应进入历史回放与首屏传输路径。

## 10. 开放问题（评审时要定）

1. **内置插件的 `mount(api)` 是否需要 `api.fs`？** 现在内置能力直接调 `ctx.get('fs')`，走 `PluginApi.fs` 会多一层间接。
2. **第三方插件能否 `provides` 服务（不只是 contributes）？** 如果能，其他插件依赖它就会引入跨进程依赖，复杂度陡增。建议**先不允许**。
3. **配置从哪来？** 现在内置的配置写在代码里（`runtime-composition`），要不要挪到 `settings`（像 `orchestration.*` 那样）？
4. **禁用内置能力后，依赖它的插件怎么办？** 装配期报错，还是自动降级？建议报错。
5. **创造模式的模板要不要支持 TypeScript**？DSH 用 TS + 构建。Lcode 的插件是宿主进程内直接 `import`（见 §9.6），TS 需要先 build——这会显著抬高门槛。**建议先用纯 ESM JavaScript 模板**（零构建），TS 作为可选。
6. **`contributes` 与实际注册的一致性校验放在哪？** 现在 `#registerTool` 已经在检查（未声明即抛），但那是**加载后**。要不要在安装时就静态检查一遍（不执行代码）？静态检查更安全但会漏掉动态注册的情况。
7. **验证清单里"从零装一遍"要不要自动化？** DSH 有完整的验证矩阵，但那是给人类开发者读的。模型造插件时，能不能提供一个 `lcode plugin verify <path>` 命令自动跑完？
