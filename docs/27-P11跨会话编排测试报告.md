## 0. 真实模型端到端验收（2026-11-09 补）

单元测试用的是回放适配器，能验证契约但不能证明"真的能用"。这一节是**不打桩**的实测。

脚本：[`scripts/smoke-orchestration.mjs`](../scripts/smoke-orchestration.mjs)
（`.\node_modules\.bin\tsx.cmd scripts/smoke-orchestration.mjs --mode auto`）

模型：本机配置的 `custom-qwen3-8-27b / qwen3.8-27b`（百炼），即当前默认模型。

### 0.1 `auto` 档：完整编排链路

```
[3] Router 工具调用: dispatch_worker, dispatch_worker   ← 模型自己决定派发
[4] 派发事件: 2 （真实 2 / 预演 0）
[6] 完成 worker 数: 2 / 2
[7] Router 总回合数: 2          ← 1 派发 + 1 合并汇报
[8] 系统汇报条数: 1             ← 合并成一条
[8b] 时间线：
      +     0ms  turn/start
      + 11816ms  worker/dispatched  task-1
      + 11832ms  worker/dispatched  task-2
      + 22488ms  worker/completed  task-1
      + 22691ms  turn/start          ← 203ms 后（正是 200ms 批处理窗口）
      + 22828ms  worker/completed  task-2
[结论] auto 档：2 个 worker 全部完成，Router 2 回合 / 1 条汇报
```

worker 的实际产出（真实读取了仓库文件）：

- worker A：`REPORT_WINDOW_MS = 200`、位置 `packages/core/orchestration-local/src/index.ts:23`
- worker B：`intervalMs` 缺省 `5 * 60 * 1000 = 300000ms`、位置 `registerLocalWatchdog`

**耗时约 26s**（含模型两轮判断 + 两个 worker 各读一遍文件）。

### 0.2 `observe` 档：只记录不执行

```
[3] Router 工具调用: dispatch_worker, dispatch_worker
[4] 派发事件: 2 （真实 0 / 预演 2）
[5] observe 档：没有真实 worker，跳过等待（这就是预期行为）
[7] Router 总回合数: 1
[8] 系统汇报条数: 0
[结论] observe 档：记录 2 条派发意向，未创建任何 worker（符合预期）
```

关键观察：**`observe` 档下 Router 仍在调用模型做判断**（它确实调了 `dispatch_worker`），
只是那一步被拦成"预演记录"。这也说明 Router 模型配置**现在就有意义**，不是等 `auto` 才生效。

### 0.3 真实跑测暴露并修复的问题

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | `EL-NO_ADAPTER` | 脚本直接建 runtime，没走 `createDesktopModelFeature()` 注册适配器 | 照主进程顺序：先建 feature，再 `createAgentRuntime({ services: feature.services })` |
| 2 | `EL-CREDENTIAL_MISSING` | 想把配置复制到临时 home，但凭据记录在 `index.db` 的 `credentials_refs` 表，只复制 `credentials/` 目录无效 | 直接用真实 home |
| 3 | `ES-SESSION_NOT_FOUND`（清理时） | 删会话前没先 `agents.dispose()`，流式回调仍往已删会话写 | 照主进程 `lcode:session.delete` 的顺序：先 dispose agent 再删 |

> 第 3 条特别值得记：**产品侧本来就是对的**（主进程删除会话会先 dispose agent），
> 是冒烟脚本绕过了那层保护。这说明"用真实入口跑"能暴露脚本自己的假设错误。

### 0.4 未观测到的东西

- **token 统计为 0**：`qwen3.8-27b` 未回传 `usage`，属模型侧行为，不是缺陷。
- **批处理只在近同时完成时合并**：实测两个 worker 完成时间差 340ms 时合并成 1 条；
  差 23s 时分成 2 条（这是**正确行为**，200ms 窗口的语义就是"几乎同时"）。

## 3. 逐条验收结论

### 3.1 事件契约（26 §4）

| 断言 | 结果 |
| --- | --- |
| 派发后 Router 会话落 `worker/dispatched`，含 `taskId`/`workerSessionId`/`reason` | ✅ |
| worker 结束落 `worker/completed`，含 `outcome`/`summary`/`artifacts` | ✅ |
| worker 是**独立会话**：自己的日志有完整回合 | ✅ |
| worker 会话 `parent_session` 指向 Router（归属，非继承） | ✅ |
| 全链路可回放：`sessions.replay` 能重建到最后一个事件 | ✅ |

### 3.2 取消隔离（26 §6）

| 断言 | 结果 |
| --- | --- |
| Router 被 `agents.cancel` 后，worker **继续执行**并最终完成 | ✅ |
| `workers.cancel` 显式取消生效（只取消当前 turn，不销毁会话） | ✅ |
| `cancel` 未知 id 返回 `false` 而非抛错 | ✅ |

**这是与 subagent 相反的一条**：subagent 走取消传播（P10-05），worker 走取消隔离。两套语义并存且互不干扰，已被测试分别钉住。

### 3.3 Router 不持有执行工具（26 §3.2）

实测 Router 会话的 `request/header` 工具清单：

```
["read","glob","grep","todo_write","delegate","delegate_async",
 "delegate_wait","dispatch_worker","skill_list","skill_load"]
```

| 断言 | 结果 |
| --- | --- |
| 不含 `shell` / `write` / `edit` / `terminal` / `run_code` | ✅ |
| **含** `dispatch_worker`（能派发） | ✅ |

> **实现期发现的缺陷**：最初把 `dispatch_worker` 误列进 `EXECUTION_TOOLS` 黑名单，
> 导致 Router 连派发工具都没有（"因噎废食"）。这条测试是发现它的唯一途径。

### 3.4 三档授权（26 §7.4）

| 断言 | 结果 |
| --- | --- |
| 默认档 = `observe` | ✅ |
| `off` 拒绝派发 | ✅ |
| `observe` 只记录 `worker/dispatched`，**不建会话、不调模型** | ✅ |
| `auto` 真正派发 | ✅ |

### 3.5 并发与深度（26 §7.5）

| 断言 | 结果 |
| --- | --- |
| 超过 `maxConcurrentWorkers` 时**排队**，不拒绝 | ✅ |
| 排队后能拿到独立 worker 会话 | ✅ |
| worker 不能派发 worker（`orchestration.dispatch` 抛错） | ✅ |
| worker 不能派发 worker（`dispatch_worker` 工具层拒绝） | ✅ 双重防线 |

### 3.6 自动汇报（26 §5.4）

| 断言 | 结果 |
| --- | --- |
| 有产出的 worker 完成后，Router 自动开新一轮 | ✅ |
| 汇报文本含 `taskId`，便于追问 | ✅ |
| 无产出不主动开口 / 失败必须开口 | ✅（`shouldReport` 单测覆盖） |
| **同一批完成的 3 个 worker 只唤醒 Router 一次**（200ms 批处理窗口） | ✅ |
| 合并汇报列出全部 taskId，失败排在最前 | ✅ |

> **实现期发现的缺陷**：最初用 `ctx.get('agents').list().followup()` 唤醒 Router，
> 实测**会话里一条事件都没有**——内核 `AgentHandle.followup` 只入队、不驱动 `drain()`。
> 真正的驱动在 agent-loop 包装后的 `LoopHandle`，必须走 `agentLoop.resume()`。
>
> **批处理是后补的**：初版每完成一个 worker 就唤醒一次 Router，并行度越高打扰越密集。
> 加 200ms 窗口 + 每 Router 10s 冷却后，3 个 worker 只触发 1 次唤醒（有专项断言）。

### 3.7 Watchdog（26 §8）

| 断言 | 结果 |
| --- | --- |
| 空会话不产生发现 | ✅ |
| `turn/end(error)` 且无后续用户消息 → `silent-failure` | ✅ |
| 用户再说话后该发现消失 | ✅ |
| `running` 超时无新事件 → `stalled` | ✅ |
| **巡检后不产生任何 worker 会话、不落 `worker/dispatched`** | ✅ |

最后一条是本套件最重要的断言：它把"只通知不派发"从文档承诺变成可执行检查。

**已挂进 runtime**（2026-11-09 补齐）：`mountPolicyBundle` 里注册，5 分钟一轮，可用
`watchdogIntervalMs` 覆盖；`onFindings` 只把结论交给调用方，**不做任何派发动作**。

### 3.8 Router 专用模型（P11-10，26 §3.2）

| 断言 | 结果 |
| --- | --- |
| 配了 `routerModel` 后，Router 会话的 `request/header` 用该模型 | ✅ |
| 普通会话**不受影响**，仍用默认模型 | ✅ |
| 未配 `routerModel` 时 Router 跟随默认模型（行为与之前一致） | ✅ |
| 设置持久化：`orchestration.routerModel` 写入 / 读回 / 置 `null` 复位 | ✅ |

> **实现期发现的缺陷**：`settings.setByKey('orchestration.routerModel', ...)` 直接抛
> `未知的设置命名空间：orchestration`——命名空间必须在 `model-feature.ts` 里
> `registerNamespace` 显式注册。这个失败点在 IPC 深处，**UI 上的表现会是"点了没反应"**，
> 所以是先用脚本直接打设置服务才发现的。

**接线路径**（四层，缺一层都不通）：

```
Settings.tsx「编排模型」区  →  preload orchestration.setRouterModel
  →  main.ts 写 settings.orchestration.routerModel
  →  agentRuntime 启动时读出来构造 createModelRouter 规则
  →  engine 在回合开始把 sessionRole 传给路由 → 命中 role:'router' 规则
```

`observe` 档下这条同样生效：Router 在决策时就在调模型，配轻模型立刻省钱。

### 3.9 桌面 UI 接入（P11-12）

| 能力 | 入口 | 验证 |
| --- | --- | --- |
| 新建编排调度会话 | 首页输入框下方「作为编排调度会话」勾选 → `session.create` 带 `role: 'router'` | 建完立刻在 `sessions.list` 里读到 `role = router` |
| 编排档位切换 | 设置 → 模型 → 「编排档位」`关闭 / 只观察 / 自动执行` | 读运行时当前值，改完即刻生效 |
| Router / worker 标记 | 侧栏 Router 行带「调度」徽标 + worker 计数；worker 缩进挂在 Router 下 | worker 行 `role = worker` 且 `parent_session` 指向 Router |
| 在途 worker 状态 | 会话页状态条：「worker N」气泡 → 展开列表，可单独取消 | 仅显示在途；已完成的通过汇报进入对话流 |

**新增数据层**：`sessions.role` 投影列（迁移 v2）。侧栏要按角色分组，而它每次列几十个会话——
让渲染层逐个读 JSONL 找 `session/role` 事件不可接受，所以把角色变成索引的一部分（`index rebuild` 会重算）。

**实现期发现的两个缺陷**（都表现为"UI 上看着没生效"）：

1. **`setRole` 后不 flush**：角色只追加了事件，而侧栏读的是索引。不 flush 的话，
   新建的 Router 会话要等用户发第一句话才显示徽标。
2. **worker 只设了 `parent_session` 没设 `role`**：`parent_session` 只说明"谁派的"，
   说明不了"它是什么"。结果 worker 既不缩进、又出现在顶层列表里。

### 3.11 上下文纪律修正（P11-14，对照官方原型）

对照官方设计复查后，发现两处**已实现能力被打了折扣**的缺陷（不是缺功能，是做错了细节）：

| # | 缺陷 | 后果 | 修复 |
| --- | --- | --- | --- |
| 1 | 汇报只带 `taskId`，不带 `workerSessionId` | **Chain of Recall 断裂**：Router 拿不到会话 id，无法 `@session:` 回溯 worker 细节。`worker/completed` 事件里虽有 id，但它不是 surface 事件、不进模型可见历史 | 汇报头改为 `worker <taskId> 已完成｜会话 @session:<workerSessionId>` |
| 2 | `summary` 是 worker 最后一条 assistant 全文，无上限 | Router 上下文被长文填满（派 10 个 worker 就是 10 段长文常驻） | 单条上限 500 字、合并汇报每条 200 字；超限时**显式写出**"摘要已截断，原长 N 字，完整内容见上面的会话"——不写这句模型会以为摘要就这些 |

**关键取舍**：截断只发生在"给模型看的汇报"。`worker/completed` 事件里仍保留**完整摘要**——
审计事实不能因为展示需要而丢失（有专项断言锁死这一点）。

**验证**：
- 汇报文本含 `@session:<workerSessionId>`（断言）
- 超长摘要被截断且带提示（断言）
- 事件里保留全文（断言）
- 端到端实测：Router 消息里写 `@session:<workerId>` 后，**其下一次请求确实包含 worker 的内部输出**（探针确认 `true`）

### 3.12 按会话的编排档位（P11-15）

原设计档位是**全局一个值、默认 `observe`**，与「勾选 Router 就代表这次要拆任务」的定位冲突：
勾了之后 Router 仍回"已记录，你没切档"，等于把同一个意图问两遍，且看起来像功能坏了。

改为**按会话定档**：

| 断言 | 结果 |
| --- | --- |
| 全局 `observe` 时，单独把某会话设为 `auto` 只影响那个会话 | ✅ 同批派发：A 得到 `materialized=true`，B 仍为预演 |
| 档位切换落 `orchestration/mode` 事件，最后一条生效 | ✅ 两次切换 → 2 条事件，`modeFor` 返回后者 |
| 新建 Router 会话按设置写入档位（默认 `auto`） | ✅ 见 §3.9 的创建链路 |

**实现要点**：`OrchestrationService` 增加 `modeFor(sessionId)`；解析顺序是
"该会话最近一条 `orchestration/mode` 事件 → 全局兜底值"。工具与 `dispatch` 都改用它，
不再读全局 `mode()`。

**顺带修掉的收尾竞态**：`auto-compaction` 的 `agent/pre-step` 处理器直接 `ctx.get('agents')`，
装配层拆服务时在途回合仍可能跑到它，抛 `service not found` 把正常收尾记成失败。
压缩是优化不是正确性，拿不到服务就跳过。

### 3.13 门禁（P11-05）

新增 `scanOrchestrationBoundaries`，两条静态检查：

| 检查 | 违规表现 | 结果 |
| --- | --- | --- |
| worker 不得继承 Router 的 `approvalPolicy` / `preset` / `approval` | `check:invariants` 变红 | ✅ 通过 |
| 派发工具必须含"worker 不能派发 worker"判定 | 缺判定即违规 | ✅ **曾正确拦截**（补判定前确实变红） |

## 4. 实现期发现并修复的缺陷

按严重度排列，全部有测试锁定：

| # | 缺陷 | 后果 | 修复 |
| --- | --- | --- | --- |
| 1 | Router 工具表误过滤 `dispatch_worker` | Router 完全无法派发（功能不可用） | 拆分 `EXECUTION_TOOLS` 与 `WORKER_FORBIDDEN_TOOLS` |
| 2 | 用内核 `AgentHandle.followup` 唤醒 Router 无效 | 自动汇报静默失效 | 改走 `agentLoop.resume()` 拿 `LoopHandle` |
| 3 | `sessions.create` 不支持 `parentSessionId` | worker 归属无法标记，审计链断 | 补参并透传到 `FileHeader.parentSession` |
| 4 | 编排 `dispose` 只清表不停 agent | 在途 worker 向已关闭会话写事件 → 进程级 unhandled rejection | dispose 改异步，等待 `inflightRuns` 全部结算 |
| 5 | 队列在 dispose 后仍启动排队项 | 同上 | `pumpQueue` 增加 `disposed` 短路 |
| 6 | 收尾读会话时不设防 | 成功执行被误报成 failed | `safeSession` + `appendToRouter` 容错 |
| 7 | 测试自行创建 agent 却不释放 | 收尾排在 afterEach 之后 → unhandled rejection | 测试显式 `agents.dispose` |
| 8 | `setRole` 后未 flush | 新建 Router 会话的徽标要等第一句话才出现 | `session.create` 带 `role` 时立刻 flush |
| 9 | worker 只设 `parent_session` 未设 `role` | worker 不缩进、又出现在顶层列表 | `materialize` 里追加 `session/role` 事件 |
| 10 | `settings` 未注册 `orchestration` 命名空间 | 保存编排模型静默失败（UI 上"点了没反应"） | `model-feature.ts` 显式 `registerNamespace` |

> 缺陷 4/5/6/7 都表现为同一个症状：**"用例全绿但报 Errors 1"**。
> 这类问题最危险——Vitest 的 `Errors` 计数不影响 passed 数，很容易被忽略。
> 本次逐一消除，最终连续 5 次全量运行 `errors=0`。

## 8. 结论

**设计目标达成。** 26 号文档定义的九项任务（P11-01～P11-09）中八项完成并通过验收，只有 **P11-09 CLI 端到端**尚未完成；后续 P11-10～P11-14 的状态以 [25 §11.3](./25-后续开发任务清单.md) 为准，其中桌面 UI 接入与 Router 专用模型入口均已完成，验收分别见 §3.9、§3.8；
§4 记录的是实现期缺陷的修复清单，均已有对应测试锁定。

**最值得记的一条**：三条最关键的边界——Router 无执行工具、worker 不能派发 worker、
Watchdog 只通知——都不是靠代码评审保证的，而是靠测试与静态门禁。这类"架构性约束"
一旦只写在文档里，就会在下一次重构中被悄悄改掉。

**建议的下一步**（按性价比排序）：

1. **堆水位判定**——`v8HeapLimit()` 在多数环境返回 0，该保护实际未生效
2. **`maxConcurrentWorkers=8` 压测**——确认真实并发下的内存表现
3. **CLI 补件后回填 P11-09**——完成尚未交付的 CLI 端到端验收

> **已完成、不再列为下一步**：Router 专用模型配置与 `role` 路由规则（P11-10，见 §3.8）、桌面 UI 接入（P11-12，见 §3.9）。配置入口不等于已实测成本下降；`observe` 档下 Router 仍会调用模型做判断，但不调用 worker 模型。
